# DSH Desktop 启动修复总结

## 故障与原因

原桌面端启动失败时统一显示“DSH Web 服务启动超时（90秒）”，但本次排查发现三个相互独立的问题：安装包从 `resources/app.asar` 计算仓库相邻位置，漏掉实际源码仓库；源码尚未安装依赖和构建，npx 首次安装超过等待期限；新版后端要求用启动链接交换浏览器 Cookie，原健康检查却把 401 当成成功。

安装副本的临时修复已证明本地构建后的后端能够约 6 秒就绪。源码 v1.2.1 将修复纳入正常项目，并补齐提前失败、取消和进程清理，不需要以后手工修改安装包。

## 当前行为

- 路径采用环境变量覆盖设置的规则，安装版从实际可执行文件目录探测仓库，路径规范化后去重。显式路径不正确时不会静默下载其他后端。
- 本地源码缺少启动入口、tsx 依赖、CLI 或网页构建产物时，启动前显示具体路径和处理命令。工具探测有 5 秒上限，不检查无关的全局工具。
- 仅识别完整正式启动行中的本机、当前端口登录链接。Electron 默认会话逐跳验证同源跳转、交换 Cookie、确认最终 2xx，再显示基础地址。兼容无需登录的旧后端。
- 401、403、404、5xx 或跨域重定向不算就绪。默认 3080 无法复用时使用 3092；显式非默认端口被尊重。
- 提前退出、启动错误、90 秒超时和取消具有不同内部错误分类；界面附上相关处理建议和脱敏日志。
- 每次启动持有自己的进程、取消信号和等待状态。并发请求合并，旧进程事件不会覆盖新启动状态；Windows 使用指定 PID 的进程树清理，外部复用服务不被终止。
- 标准输出和错误输出按 UTF-8 完整行处理，先移除颜色码和隐藏登录凭据、代理密码，再截取日志。过长行整体丢弃，避免泄露凭据片段。
- 桥接后端重启接口等待实际完成，异步失败正确返回错误。
- 显式退出先进入退出状态，避免后端清理完成后窗口关闭又被“隐藏到托盘”拦截。

## 验证方式

`npm test` 包含仓库探测、缺依赖提示、模拟计时的 90 秒超时、并发启动、取消、迟到事件、进程清理、完整行脱敏，以及真实本地 HTTP 303 → Cookie → 200 测试。

`npm run test:startup -- <已构建的后端仓库>` 在 Windows 创建隔离 ASAR 安装副本，复用原项目主入口和运行模块。测试入口仅负责隔离用户数据、隐藏测试窗口和采集结果，正式包仍使用 `main.js`。验证 Electron 真实 Cookie、页面加载、桥接重启结果、凭据未进入日志，以及退出前记录的全部进程和后端端口已释放。

冒烟数据与安装副本均放在 `%USERPROFILE%\Downloads\anget-tmp\dsh-startup-smoke-*`，由脚本完成清理；不覆盖项目 `dist` 或当前安装。模型调用不是本次启动测试的一部分。
